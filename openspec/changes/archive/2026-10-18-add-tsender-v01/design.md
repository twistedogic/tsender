# Design

## Context

`twistedogic/ender` is a Rust CLI + ratatui TUI that ships today. Its simulator (in `src/main.rs`), HK tax logic, scenario loader, and `--json` output shape are the upstream reference for tsender (static vendored text only — no runtime or build dependency). There is no existing tsender code; this design starts from an empty repo. See `proposal.md` for motivation.

Constraints:

- tsender is pure TS, fully self-contained. The deployed PWA has no Rust toolchain, no backend, no external services. The simulator runs entirely in the browser.
- **No CLI.** tsender has no command-line entry point.
- **No Rust anywhere.** Dev hardware cannot build Rust; `ender` is never built, run, or diffed against — not locally, not in CI.
- Behavior is locked at v0.1 by committing canonical scenarios plus their hand-verified expected outputs (`fixtures/`). CI runs only TypeScript and the web toolchain; no Rust, no comparison to ender.
- Mobile-first responsive UI; PWA on GitHub Pages.
- No backend: scenarios live in the browser (localStorage + a downloadable YAML).

## Goals / Non-Goals

**Goals:**

- TypeScript port of the simulator conforming to the adopted specs (`scenario-loading`, `hk-salaries-tax`, `hk-property-tax`).
- Mobile-first React form covering every event type.
- Results dashboard with summary, monthly chart, and insolvency/passive-income markers.
- Scenario regression tests (`fixtures/*.expected.json`) that gate merges.
- PWA install + offline-capable shell.

**Non-Goals:**

- Compare mode (defer to a later change).
- WASM-bundled Rust core — dev hardware cannot build Rust; a WASM model would make every change depend on a build this project can never produce.
- Output parity with `ender` — dropped deliberately; tsender conforms to its specs and its committed expected outputs, not to a binary.
- Server-side rendering, API endpoints, sync, accounts.
- Visual parity with ratatui (terminal is gone; the web dashboard replaces it).

## Decisions

### Decision: Build pipeline — Vite + TypeScript + vite-plugin-pwa
Vite gives us instant dev, TS out of the box, and a battle-tested PWA plugin (`vite-plugin-pwa` with `injectManifest`/`generateSW`) for the service worker + manifest. Rollup-driven prod build, fast cold cache via Workbox.

- **Alternative considered:** Next.js — heavier than needed for a static SPA; SSR/RSC unused.
- **Alternative considered:** Create React App — deprecated; no PWA story without ejecting.

### Decision: YAML parser — `yaml` (npm)
`yaml` is the modern, schema-aware YAML 1.2 parser with first-class TypeScript types and good error messages. It matches what we need (round-trip with `serde_yaml_ng`'s output for the keys we use).

- **Alternative considered:** `js-yaml` — works, but weaker types and older API.
- **Alternative considered:** hand-roll a parser — non-trivial; the cost of YAML edge cases is not worth it.

### Decision: Chart library — uPlot
uPlot is ~40 KB, fast on large series (a 720-point monthly trajectory renders in milliseconds), and natively responsive. The data shape (`number[]` arrays for x and y) matches what the simulator produces directly.

- **Alternative considered:** Chart.js — heavier (~80 KB), animation overhead we don't need.
- **Alternative considered:** Recharts — React-ergonomic but ~100 KB and SVG-driven; slow for 720 points.
- **Alternative considered:** hand-rolled SVG — saves the dep but ~200 LOC and we own the bug surface. Skip unless uPlot proves inadequate.

### Decision: State — React `useState` + Context
The app surface is one scenario, one simulation result, one set of UI controls. No cross-cutting store, no async pipeline. `useState` in `App` plus a Context for the scenario/result pair keeps the prop-drilling manageable without a library.

- **Alternative considered:** Zustand — overkill for one slice of state.
- **Alternative considered:** Redux — same; cost ≫ benefit.

### Decision: Forms — native React inputs
Controlled `<input>` / `<select>` / `<textarea>` elements with custom validation. React's idioms cover this without a form library. The form's complexity is in the **shape** of the subforms (one per event type), not in input plumbing.

- **Alternative considered:** react-hook-form — useful when the form has hundreds of fields and performance matters; here the simulation re-run is the bottleneck, not render.
- **Alternative considered:** Formik — same.

### Decision: Scenario regression — committed expected outputs
Each canonical scenario is a pair committed to the repo: `fixtures/<name>.yaml` (input) and `fixtures/<name>.expected.json` (the expected output). On first commit, the expected file is generated by running the TS simulator once and hand-verifying a few values against the adopted specs (e.g., the progressive-tax worked example from `hk-salaries-tax`). `npm run test:scenarios` runs `runScenario(loadScenario(fixtures/<name>.yaml))` and asserts deep-equality (within `1e-9` numeric tolerance) against the expected file. Drift is caught in CI; no comparison to ender.

- **Alternative considered:** compare against `ender --json` at build time — keeps parity with ender fresh, but requires a Rust toolchain in CI and conflicts with the self-contained constraint. Rejected.
- **Alternative considered:** vitest's built-in `toMatchSnapshot()` — standard but hides the expected output in `__snapshots__/` next to the test, making review less ergonomic. Hand-committed `.expected.json` files at `fixtures/` are visible and serve as living documentation of the simulator's output.

### Decision: Float comparison tolerance — exact equality, allow `1e-9` absolute delta
Both Rust `f64` and JS `Number` are IEEE 754 64-bit, so for purely deterministic, order-preserving operations they match exactly. tsender compares its output against the committed `fixtures/*.expected.json` files with `Math.abs(a − b) < 1e-9` to absorb rounding in `JSON.stringify` (which uses `Number.toString`).

- **Alternative considered:** tolerance-based comparison only — masks real divergence.

### Decision: Service worker — precache app shell, no runtime fetch
The app makes no network calls. `vite-plugin-pwa` `generateSW` strategy: precache the build output, no runtime caching. Users get offline after first visit; nothing else to invalidate.

### Decision: Mobile input affordances — native HTML types
`<input type="number" inputMode="decimal">` for decimals, `<input type="month">` for `YYYY-MM`, `<input type="checkbox">` / `<input type="radio">` for status/age bands. Native browser keyboards (decimal pad on mobile) without JS pickers. `type="month"` is unsupported on iOS Safari and degrades to a text field there, so month inputs carry `pattern="[0-9]{4}-[0-9]{2}"`, a `YYYY-MM` placeholder, and the same validation as a typed value — supporting browsers get the native picker for free.

### Decision: Layout — CSS Grid + Flexbox, no CSS framework
~200 lines of hand-written CSS. Tailwind/UnoCSS would add a build step and a learning surface for code that's mostly one-screen anyway.

- **Alternative considered:** Tailwind — fine, but the form is the only screen and a hand-rolled stylesheet is faster to author and audit.
- **Alternative considered:** CSS-in-JS (styled-components / emotion) — runtime cost and dep weight we don't need.

## Risks / Trade-offs

- **[Risk]** Float accumulation order matters — reordering operations in the simulator produces different outputs that fail the regression tests. → **Mitigation:** the canonical scenarios exercise accumulation paths (recurring flows + reserve settlement + tax accrual); hand-verified expected files lock the accumulation order, and any reordering is caught by the test:scenarios diff.
- **[Risk]** Initial `.expected.json` files might encode a bug present at v0.1, locking the bug in as the contract. → **Mitigation:** the author hand-verifies the progressive-tax worked example from `hk-salaries-tax` and a trivial arithmetic scenario (no tax, single cashflow) before commit; both are visible in the expected files.
- **[Risk]** Service worker caches a stale app shell after deploy. → **Mitigation:** `vite-plugin-pwa` emits content-hashed asset filenames; the precache manifest invalidates on rebuild.
- **[Risk]** `localStorage` quota (~5 MB) is hit by a user pasting a giant scenario. → **Mitigation:** cap persisted state at ~256 KB; if exceeded, fall back to in-memory only with a one-time toast.
- **[Risk]** Large horizon (60 years × 12 = 720 months) makes chart re-renders choppy on low-end phones. → **Mitigation:** uPlot's canvas + downsampling; debounce simulation to 10 Hz per `results-display` spec.
- **[Risk]** Form re-runs the simulator on every keystroke; battery drain on mobile. → **Mitigation:** debounced re-run + a "Run" button for explicit control (see `results-display` spec).

## Migration Plan

No migration — repo is empty. Deploy steps:

1. Merge into `main`.
2. CI builds the PWA, runs vitest + `npm run test:scenarios`, and uploads `dist/` as a Pages artifact.
3. GH Pages serves at `twistedogic.github.io/tsender`.
4. Rollback = revert the merge commit (no data to migrate).

## Open Questions

- Do we want a basic in-app "examples" picker (a few canned scenarios) so first-time users see something runnable? Defer to v0.2; not in the spec.
- Should the chart include a third series for `monthly_cashflow`? Spec says cash + assets only; defer.
- Are we OK with shipping `tsender` without a license, mirroring `ender`'s `null` license today? Out of scope for this change but worth raising at archive time.
